# RFP Lens 최종 분석 결과 화면 설계

## 목적

요구사항이 많은 공고문에서도 사용자가 공고의 핵심 조건과 검토 진행 상태를 한 화면에서 파악할 수 있게 한다. 핵심 요약은 현재 설정된 AI 공급자가 작성하되, 모든 요약 문구는 이미 추출된 요구사항 ID와 연결하고 서버에서 그 연결을 검증한다. 통계와 상태는 AI가 아닌 데이터베이스 값으로 계산한다.

## 사용자 경험

프로젝트에 분석 결과가 있으면 프로젝트 상세, 요구사항 검토, 컴플라이언스 화면에서 `최종 분석 결과`로 이동할 수 있다. 경로는 `/projects/:projectId/overview`로 한다.

화면은 승인된 A안인 균형형 레이아웃을 사용한다.

1. 상단 통계에는 `전체 요구사항`, `확정·수정`, `검토 대기`, `근거 확인 필요`를 표시한다.
2. 본문 왼쪽에는 지원 자격, 예산, 일정, 제출, 평가, 기술 목표의 핵심 조건을 표시한다.
3. 본문 오른쪽에는 확정·수정, 검토 대기, 제외 건수와 검토 완료율을 표시한다.
4. 핵심 조건을 선택하면 연결된 요구사항 목록과 원문 근거 위치를 표시하고, `요구사항 검토에서 열기`로 해당 항목에 이동한다.
5. 기본 범위는 검토가 하나도 시작되지 않았으면 전체 비제외 요구사항이고, 확정 또는 수정 항목이 하나라도 있으면 확정·수정 항목이다.
6. `검토 전 항목 포함`을 켜면 전체 비제외 요구사항 기준 요약으로 전환한다.
7. AI 요약이 아직 생성 중이면 통계는 즉시 표시하고 핵심 조건 영역에 생성 상태를 표시한다.
8. AI 요약에 실패하거나 유효한 핵심 조건이 없으면 분류별 요구사항을 원문 그대로 나열하는 결정적 대체 화면을 표시한다.

## 데이터 정확성과 신뢰 경계

AI에는 원본 문서 전체를 다시 보내지 않는다. 서버가 선택한 요구사항의 다음 필드만 전달한다.

- 요구사항 ID
- 요구사항 문구
- 분류
- 필수 여부
- 신뢰도
- 검토 상태
- 검증된 근거 인용문

AI는 구조화된 결과로 분류별 `headline`, 짧은 `detail`, `requirement_ids`만 반환한다. 서버는 다음 조건을 모두 만족하는 항목만 저장한다.

- 반환된 요구사항 ID가 입력 집합에 존재한다.
- 반환된 ID의 요구사항 분류가 요약 분류와 일치한다.
- 요약 항목에 하나 이상의 유효한 요구사항 ID가 있다.
- 문구 길이가 정의된 최대 길이를 넘지 않는다.

AI가 반환한 문구 자체를 원문 사실로 간주하지 않는다. 화면에는 항상 연결된 요구사항 수와 근거 보기 동작을 함께 제공한다. 통계, 검토 완료율, 미검증 근거 수는 서버가 데이터베이스에서 계산하며 AI 응답에서 받지 않는다.

## 요약 범위

두 범위를 독립적으로 캐시한다.

- `all`: 제외 상태가 아닌 모든 요구사항
- `reviewed`: 확정 또는 수정 상태인 요구사항

검토 시작 여부는 프로젝트의 `confirmed` 또는 `edited` 요구사항 존재 여부로 판단한다. `reviewed` 범위가 비어 있으면 화면은 자동으로 `all` 범위를 사용한다.

분류별 핵심 조건은 기존 `RequirementCategory`를 그대로 사용한다. 첫 화면의 핵심 영역에는 업무상 우선순위가 높은 여섯 분류를 고정 순서로 노출한다.

1. `eligibility`
2. `budget`
3. `schedule`
4. `submission`
5. `evaluation`
6. `technical_goal`

`exclusion`, `quantitative_target`, `other`는 분류별 상세와 통계에는 포함하지만 첫 화면 핵심 카드에는 포함하지 않는다.

## 저장 모델

새 `analysis_summaries` 테이블을 추가한다.

- `id`: UUID
- `project_id`: 프로젝트 외래 키
- `scope`: `all` 또는 `reviewed`
- `state`: `pending`, `running`, `succeeded`, `failed`
- `provider`: 사용한 공급자
- `model`: 사용한 모델
- `prompt_version`: 요약 프롬프트 버전
- `source_fingerprint`: 해당 범위 요구사항의 ID, 수정 시각, 검토 상태로 만든 SHA-256
- `highlights`: 검증을 통과한 구조화 JSON
- `error_code`, `error_message`: 실패 정보
- `started_at`, `completed_at`, `created_at`, `updated_at`

프로젝트와 범위 조합에는 유일 제약을 둔다. API는 현재 요구사항으로 계산한 fingerprint와 저장된 fingerprint가 다르면 결과를 `stale`로 표현하고 재생성 작업을 예약한다. 기존 성공 결과가 있으면 새 결과가 준비될 때까지 이전 결과를 유지하되 화면에 `업데이트 중`을 표시한다.

요구사항 삭제나 문서 재분석으로 연결 ID가 사라질 수 있으므로 응답 직전에 현재 프로젝트 소유권과 요구사항 존재 여부를 다시 검증한다.

## 생성 흐름

1. 문서 분석이 `review_required` 또는 `partial`로 끝나면 `all` 요약 생성을 예약한다.
2. 요구사항이 확정, 수정, 제외되면 `all`과 `reviewed`의 fingerprint가 자연스럽게 변경된다.
3. 최종 분석 결과 API를 호출할 때 필요한 범위의 캐시가 없거나 stale이면 Celery 작업을 멱등하게 예약한다.
4. 작업은 현재 UI 설정을 `resolve_runtime_settings`로 읽고 기존 OpenAI, local, fake 공급자 선택을 따른다.
5. 작업은 선택 범위의 요구사항을 분류별로 묶어 한 번의 구조화 요약 요청으로 보낸다.
6. 서버는 반환된 ID와 분류를 검증한 뒤 성공 결과를 원자적으로 저장한다.
7. UI는 생성 중일 때 2초 간격으로 다시 조회하고 성공 또는 실패 시 폴링을 중단한다.

동일한 `project_id`, `scope`, `source_fingerprint`에 대한 중복 작업은 예약하지 않는다. 작업 시작 시 행 잠금으로 다시 확인해 동시 요청도 하나만 실행되게 한다.

## AI 공급자 인터페이스

기존 요구사항 추출 공급자와 요약 공급자의 책임을 분리한다. 새 `SummaryProvider` 프로토콜은 구조화된 요구사항 목록을 받아 `SummaryBatch`를 반환한다.

- OpenAI 공급자는 Responses 구조화 출력 형식을 사용한다.
- Local 공급자는 현재 llama.cpp 호환 JSON schema 방식과 300초 타임아웃, SDK 재시도 비활성화 정책을 재사용한다.
- Fake 공급자는 테스트와 demo 환경에서 고정된 분류별 요약을 반환한다.

요약 프롬프트는 새로운 버전 `analysis-summary-v1`로 관리한다. 한 분류에 여러 요구사항이 있어도 근거에 없는 숫자, 날짜, 기관명, 조건을 새로 만들지 말고 입력 요구사항을 압축하도록 지시한다.

## API

### `GET /api/projects/{project_id}/analysis-overview?scope=auto|all|reviewed`

응답은 다음 구조를 사용한다.

```json
{
  "effective_scope": "reviewed",
  "summary_state": "succeeded",
  "stale": false,
  "stats": {
    "total": 41,
    "confirmed_or_edited": 25,
    "pending": 11,
    "rejected": 5,
    "unverified_evidence": 5
  },
  "category_counts": {
    "eligibility": 5,
    "budget": 6
  },
  "highlights": [
    {
      "category": "budget",
      "headline": "과제당 최대 20억 원",
      "detail": "민간부담금 및 현물 계상 조건 포함",
      "requirement_ids": ["uuid"]
    }
  ],
  "fallback_requirements": [],
  "updated_at": "2026-08-27T00:00:00Z"
}
```

`stats`는 선택 범위와 관계없이 프로젝트 전체 검토 현황을 나타낸다. `category_counts`, `highlights`, `fallback_requirements`는 `effective_scope` 기준이다. `summary_state`가 `pending` 또는 `running`이면 API는 `202 Accepted`가 아니라 `200 OK`로 통계와 현재 상태를 반환해 화면이 부분적으로 렌더링될 수 있게 한다.

## 프런트엔드 구성

새 기능 디렉터리 `frontend/src/features/overview/`를 사용한다.

- `AnalysisOverviewPage.tsx`: 데이터 조회, 범위 전환, 폴링, 오류 상태
- `OverviewStats.tsx`: 정확한 통계와 검토 완료율
- `CoreHighlights.tsx`: 여섯 핵심 분류 카드와 선택 상태
- `ReviewProgress.tsx`: 검토 진행 막대와 우선 확인 메시지
- `HighlightEvidence.tsx`: 선택한 요약의 연결 요구사항과 근거
- `overview.ts`: 기본 범위 결정 및 표시용 파생 계산

요구사항 검토 페이지는 URL 쿼리 `requirement=<id>`를 읽어 해당 카드를 선택하고 목록 내 위치로 이동한다. 존재하지 않거나 현재 필터에 없는 ID이면 첫 번째 항목을 선택한다.

모바일에서는 핵심 조건, 검토 진행, 근거 상세 순서로 한 열에 배치한다. 색상만으로 상태를 표현하지 않고 텍스트와 숫자를 함께 사용한다.

## 오류 및 빈 상태

- 분석 결과가 없으면 프로젝트 상세로 돌아가는 안내를 표시한다.
- `reviewed` 범위가 비어 있으면 `all`로 자동 전환하고 검토 전 항목 기준임을 표시한다.
- 일부 분류에 요구사항이 없으면 해당 핵심 카드를 숨긴다.
- AI 공급자 연결 실패, 타임아웃, 잘못된 JSON, 잘못된 ID는 요약 작업 실패로 기록한다.
- 실패 시 통계와 분류별 원문 요구사항 대체 화면은 계속 제공한다.
- stale 요약은 숨기지 않고 `업데이트 중` 표시와 함께 제공한다.
- 사용자가 다른 프로젝트의 요구사항 ID를 URL에 넣어도 소유권 검증을 통과하지 못하며 노출하지 않는다.

## 테스트 전략

### 백엔드 단위 테스트

- 요구사항 상태별 통계와 검토 완료율 계산
- `auto` 범위 선택 규칙
- fingerprint 결정성과 변경 감지
- AI가 존재하지 않는 ID 또는 다른 분류 ID를 반환할 때 제거
- 유효 항목이 하나도 없을 때 fallback 생성
- OpenAI, local, fake 요약 공급자의 구조화 응답 계약

### 백엔드 통합 테스트

- 프로젝트 소유자만 overview를 조회
- 캐시가 없을 때 생성 작업이 한 번만 예약
- stale 캐시에서 이전 결과와 갱신 상태를 함께 반환
- 요구사항 수정 후 fingerprint 변경
- 실패한 AI 요약에서도 통계와 fallback 반환

### 프런트엔드 테스트

- 통계와 핵심 카드 렌더링
- 기본 범위와 `검토 전 항목 포함` 전환
- 생성 중 폴링과 실패 fallback
- 핵심 카드 선택 시 연결 근거 표시
- 요구사항 검토 링크에 정확한 requirement ID 포함
- 모바일 레이아웃의 콘텐츠 순서

### E2E

기존 HWPX 분석 흐름에 최종 분석 결과 진입을 추가한다. fake provider로 통계, 핵심 조건, 연결 근거를 확인하고 해당 요구사항 검토 화면으로 이동한 뒤 기존 XLSX 내보내기까지 검증한다.

## 이번 범위에서 제외

- 사용자가 직접 요약 문구를 편집하는 기능
- 요약 PDF 또는 별도 보고서 내보내기
- 여러 프로젝트의 비교 대시보드
- AI가 원본 전체 문서를 다시 읽는 별도 질의응답 기능
- 청크별 분석 진행률 화면
- 요약 히스토리 및 버전 간 비교

## 완료 기준

- 긴 공고문에서도 최종 분석 결과 페이지가 통계부터 즉시 표시된다.
- 핵심 조건은 현재 설정된 AI 공급자로 생성되고 실제 요구사항 ID와 근거에 연결된다.
- 검토 전과 검토 후 범위를 전환할 수 있다.
- AI 요약이 실패해도 정확한 통계와 분류별 원문 요구사항을 확인할 수 있다.
- 사용자는 핵심 조건에서 해당 요구사항 검토 위치로 이동할 수 있다.
- 백엔드, 프런트엔드, E2E 테스트와 컨테이너 빌드가 통과한다.
